# Spec: Custom Dashboard (F6)

> Version: v1.2  
> Status: Design  
> Dependencies: v1.0 (Cases, Log Sources), v1.1 (Smart Baselines)

---

## Problem Statement

The current `dashboard.html` is a static summary page with hardcoded widgets. It cannot be configured by the operator. There is no way to arrange widgets differently, add more of the same type, or remove widgets that aren't relevant to a specific team's workflow. The Custom Dashboard replaces this with a configurable widget grid where analysts compose their own view.

---

## Approach: Option A — Pre-built Widget Types, Configurable Layout

**What this means:**
- A fixed set of widget types (6 in v1.2)
- Analysts pick which widgets to show and arrange them in a grid
- Layout is saved to DuckDB per user
- No drag-and-drop in v1.2 — grid position is specified by editing widget settings
- No custom code widgets, no external data sources

This is deliberately scoped small. The dashboard's primary purpose is a SOC room overview ("glass board"), not a full BI tool.

---

## Widget Types

| ID | Name | Data source | Description |
|---|---|---|---|
| `event_volume` | Event Volume | `GET /events/histogram` | Line/bar chart of event count over time; configurable time range |
| `top_sources` | Top Sources | `GET /events/facets` | Horizontal bar chart of event counts by source |
| `top_ips` | Top Source IPs | `GET /events/facets` | Horizontal bar chart of event counts by source_ip |
| `alert_severity` | Alert Severity | `GET /alerts/facets` | Donut chart of alert counts by severity |
| `recent_alerts` | Recent Alerts | `GET /alerts` | Table of N most recent alerts |
| `case_status` | Case Status | `GET /cases/facets` | Donut chart of open cases by status |
| `baseline_health` | Baseline Health | `GET /baselines/violations` | Count of unacknowledged violations + severity breakdown |

Each widget type has a set of configuration options (time range, limit, title override, etc.).

## Data Model

### New Table: `dashboards`

One row per user's saved dashboard layout.

```sql
CREATE TABLE IF NOT EXISTS dashboards (
    dashboard_id    VARCHAR PRIMARY KEY,
    owner           VARCHAR NOT NULL UNIQUE,   -- username; one dashboard per user
    title           VARCHAR NOT NULL DEFAULT 'My Dashboard',
    widgets         JSON NOT NULL,             -- ordered array of widget configs
    created_at      TIMESTAMP NOT NULL,
    updated_at      TIMESTAMP NOT NULL
);
```

`widgets` JSON schema (array):

```json
[
  {
    "widget_id": "uuid",
    "type": "event_volume",
    "title": "Events (last 24h)",
    "grid_position": { "row": 0, "col": 0, "width": 2, "height": 1 },
    "config": {
      "time_range": "24h",
      "buckets": 48
    }
  },
  {
    "widget_id": "uuid",
    "type": "top_ips",
    "title": "Top 10 Source IPs",
    "grid_position": { "row": 0, "col": 2, "width": 1, "height": 1 },
    "config": {
      "limit": 10,
      "time_range": "7d"
    }
  }
]
```

**Grid model:** a 3-column grid. `width` values: 1, 2, or 3. `height` values: 1 or 2. Row and column are zero-indexed. The renderer packs widgets into the grid top-to-bottom, left-to-right.

## API Design

### `GET /dashboard`

Get the current user's saved dashboard. Returns a default dashboard with 4 widgets if none saved.

**Response:**
```json
{
  "dashboard_id": "uuid",
  "owner": "alice",
  "title": "My Dashboard",
  "widgets": [...]
}
```

### `PUT /dashboard`

Save (create or replace) the current user's dashboard layout.

**Request:** full dashboard object with `title` and `widgets` array.

**Response:** `200` with saved dashboard.

### `DELETE /dashboard`

Reset to default (deletes the custom layout).

These are user-scoped — each user has their own dashboard. Admins cannot edit another user's dashboard.

## UI Design

### `ui/dashboard.html` — rebuilt

The current static `dashboard.html` is replaced entirely.

**Modes:** View mode (default) and Edit mode (toggled by "Customize" button).

#### View mode

Standard nav + topbar. Dashboard title. Grid of widgets. Each widget:

```
┌─────────────────────────────┐
│ Event Volume (24h)    [⋮]   │
│                             │
│  ▁▂▃▄▅▆▅▄▃▂▁▂▃▄▅▆▅▄▃▂      │
│  Mon           Tue          │
│                             │
│  Total: 14,203 events       │
└─────────────────────────────┘
```

`[⋮]` button shows widget actions: Refresh, Edit settings, Remove.

Auto-refresh: widgets independently refresh every 60 seconds. The refresh timestamp is shown in the widget footer.

#### Edit mode

"Customize" button in topbar switches to edit mode. Header changes:

```
[Editing Dashboard]  Title: [My Dashboard]           [Save] [Cancel]
```

Each widget gains a visible border and an edit overlay:

```
┌─────────────────────────────┐
│  ▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒  ×  │
│         [Edit]              │
│                             │
│  Event Volume (24h)         │
└─────────────────────────────┘
```

`×` removes the widget. `Edit` opens a widget settings form.

**"+ Add Widget" button** appears below the grid in edit mode. Opens a picker:

```
Select widget type:
○ Event Volume       ○ Top Sources
○ Top Source IPs     ○ Alert Severity
○ Recent Alerts      ○ Case Status
○ Baseline Health

[Add]
```

After picking type, a settings form appears (title, config options). Widget is added at the end of the grid.

**Widget settings form (example: Event Volume):**
```
Title: [Event Volume (24h)          ]
Time range: (● 1h) (○ 6h) (● 24h) (○ 7d)
Grid width: (○ 1 col) (● 2 cols) (○ 3 cols)
```

Saving widget settings updates the local `S.widgets` array. Clicking "Save" in the header writes the full layout to `PUT /dashboard`.

## Export

**PDF:** `window.print()` with `@media print` CSS rules that remove the topbar, nav, edit controls, and render the widget grid full-width.

**HTML snapshot:** `POST /dashboard/export/html`

The server renders a self-contained HTML file: it fetches current data for all widgets, inlines the data as JSON in script tags, and returns a static HTML file that renders without network calls. The file is returned as a file download (`Content-Disposition: attachment`).

This is simpler than a headless browser screenshot and works in any browser.

**Request:** `POST /dashboard/export/html` (no body).

**Response:** `200` with `Content-Type: text/html`, `Content-Disposition: attachment; filename="dashboard-{timestamp}.html"`.

## Technical Notes

- Dashboard data is user-scoped. The `owner` field is the JWT username — the server never accepts `owner` from the request body.
- The `PUT /dashboard` endpoint replaces the full `widgets` array — no partial update. The client always sends the complete current layout.
- Widget `widget_id` is generated client-side (UUID) when the user adds a widget. Server stores and returns it unchanged.
- `renderer.py` for HTML export calls internal API functions (not HTTP) to avoid auth overhead. It runs inline in the request handler — acceptable for a low-frequency export operation.
- Max widgets per dashboard: 20 (validated at API level). This prevents a pathologically large dashboard.

## Out of Scope

- Drag-and-drop rearrangement (complex JS for v1.2; position editing via form is sufficient)
- Multiple named dashboards per user (one per user in v1.2)
- Shared/team dashboards (each user has their own)
- Custom widget code or embedding external URLs
- Real-time streaming widgets (WebSockets/SSE)
- Dashboard templates
- PNG/image screenshot export (requires headless browser; HTML export is sufficient)
