# Spec: Cases & Workflow (F1)

> Version: v1.0  
> Status: Design  
> Dependencies: v0.9 (audit log, JWT auth, users table)

---

## Problem Statement

The current alert model is a flat JSONL file with a single triage note field. Analysts cannot track investigation progress across multiple related alerts, collaborate with comments, assign ownership, or record why an alert was closed. This makes post-incident review impossible and provides no institutional memory.

---

## User Stories

1. As an **analyst**, I can escalate one or more alerts into a Case so I can track a multi-alert investigation as a single unit.
2. As an **analyst**, I can add threaded comments to a case — each comment records who wrote it and when, so the investigation timeline is preserved.
3. As an **analyst**, I can assign a case to myself or another user so ownership is clear.
4. As an **analyst**, I must choose a resolution type (True Positive / False Positive / Benign / Undetermined) when I close a case — it cannot be skipped.
5. As a **manager**, I can see all open cases, their assignees, and their comment count to understand team workload.
6. As an **admin**, every case action (create, comment, assign, close) is recorded in the audit log.

---

## Data Model

### New Table: `cases`

```sql
CREATE TABLE IF NOT EXISTS cases (
    case_id         VARCHAR PRIMARY KEY,
    title           VARCHAR NOT NULL,
    description     VARCHAR,
    severity        VARCHAR NOT NULL DEFAULT 'medium',  -- low|medium|high|critical
    status          VARCHAR NOT NULL DEFAULT 'open',    -- open|investigating|resolved
    resolution      VARCHAR,                            -- true_positive|false_positive|benign|undetermined
                                                        -- required when status = 'resolved'
    assignee        VARCHAR,                            -- username; FK to users (soft)
    created_by      VARCHAR NOT NULL,
    created_at      TIMESTAMP NOT NULL,
    updated_at      TIMESTAMP NOT NULL,
    closed_at       TIMESTAMP,
    mitre_tactic    VARCHAR,
    mitre_technique VARCHAR,
    tags            JSON                                -- array of strings
);

CREATE INDEX IF NOT EXISTS idx_cases_status   ON cases(status);
CREATE INDEX IF NOT EXISTS idx_cases_assignee ON cases(assignee);
CREATE INDEX IF NOT EXISTS idx_cases_created  ON cases(created_at);
```

### New Table: `case_alerts`

Links cases to alerts. One case can have many alerts; one alert can belong to many cases.

```sql
CREATE TABLE IF NOT EXISTS case_alerts (
    case_id     VARCHAR NOT NULL,
    alert_id    VARCHAR NOT NULL,
    linked_at   TIMESTAMP NOT NULL,
    linked_by   VARCHAR NOT NULL,
    PRIMARY KEY (case_id, alert_id)
);
```

### New Table: `case_comments`

```sql
CREATE TABLE IF NOT EXISTS case_comments (
    comment_id  VARCHAR PRIMARY KEY,
    case_id     VARCHAR NOT NULL,
    author      VARCHAR NOT NULL,               -- username
    body        VARCHAR NOT NULL,
    created_at  TIMESTAMP NOT NULL,
    edited_at   TIMESTAMP,
    is_system   BOOLEAN NOT NULL DEFAULT FALSE  -- for auto-generated timeline events
);

CREATE INDEX IF NOT EXISTS idx_case_comments_case ON case_comments(case_id);
```

System comments (`is_system = TRUE`) are auto-created by the backend on state changes:
- "Status changed from open → investigating by alice"
- "Alert nginx-http-404-spike (alert_id) linked by bob"
- "Case closed as True Positive by alice"

These give a complete audit trail without requiring analyst effort.

### No changes to the existing alerts table

Alerts remain immutable JSONL records. The `case_alerts` join table provides the link. The existing `triage_status` on the alert model stays as-is for standalone alert triage; it is independent of case status.

## API Design

Base path: `/cases`  
Auth: all endpoints require `analyst` role or above.  
Write operations (create, update, close, link alerts) also emit audit log events.

### `GET /cases`

List cases with filters.

| Param | Type | Description |
|---|---|---|
| `status` | string | `open`, `investigating`, `resolved` |
| `severity` | string | `low`, `medium`, `high`, `critical` |
| `assignee` | string | Username |
| `q` | string | Full-text on title, description |
| `start` / `end` | ISO 8601 | Filter by `created_at` |
| `limit` / `offset` | int | Pagination (default 50) |

Response:
```json
{
  "total": 12,
  "cases": [{
    "case_id": "uuid",
    "title": "Brute force attempt — 10.0.0.1",
    "severity": "high",
    "status": "investigating",
    "resolution": null,
    "assignee": "alice",
    "created_by": "bob",
    "created_at": "2026-06-29T10:00:00",
    "updated_at": "2026-06-29T11:00:00",
    "alert_count": 3,
    "comment_count": 5,
    "mitre_tactic": "Credential Access",
    "mitre_technique": "T1110",
    "tags": ["brute-force", "ssh"]
  }]
}
```

### `POST /cases`

Create a new case. The creating user is set as `created_by`. A system comment is auto-created.

Request:
```json
{
  "title": "Brute force attempt — 10.0.0.1",
  "description": "Multiple failed SSH logins followed by successful login.",
  "severity": "high",
  "assignee": "alice",
  "mitre_tactic": "Credential Access",
  "mitre_technique": "T1110",
  "tags": ["brute-force", "ssh"],
  "alert_ids": ["uuid1", "uuid2"]
}
```

`alert_ids` is optional — analyst can link alerts at creation or later.

Response: `201 Created` with the full case object.

### `GET /cases/{case_id}`

Full case detail including linked alerts and all comments.

Response:
```json
{
  "case_id": "uuid",
  "title": "...",
  "...": "all case fields",
  "alerts": [{ "alert_id": "uuid", "rule_name": "...", "severity": "...", "triggered_at": "..." }],
  "comments": [{
    "comment_id": "uuid",
    "author": "alice",
    "body": "Confirmed same IP in CloudTrail logs.",
    "created_at": "2026-06-29T11:00:00",
    "edited_at": null,
    "is_system": false
  }]
}
```

### `PATCH /cases/{case_id}`

Update case fields. All fields optional. Partial update.

```json
{
  "status": "investigating",
  "assignee": "charlie",
  "severity": "critical",
  "tags": ["brute-force", "ssh", "lateral-movement"]
}
```

Closing a case (`status: "resolved"`) **requires** `resolution` to be present. The API returns `422` if resolution is absent when closing.

```json
{ "status": "resolved", "resolution": "true_positive" }
```

Valid `resolution` values: `true_positive`, `false_positive`, `benign`, `undetermined`.

### `DELETE /cases/{case_id}`

Requires `admin` role. Soft-recommended to close instead of delete. Hard-delete removes case + comments + alert links. Audit logged.

### `POST /cases/{case_id}/comments`

Add a comment. Author is taken from the JWT (not from request body).

```json
{ "body": "Confirmed malicious. Escalating to IR team." }
```

Response: `201 Created` with the comment object.

### `PUT /cases/{case_id}/comments/{comment_id}`

Edit own comment only. Admins can edit any. Sets `edited_at`.

### `DELETE /cases/{case_id}/comments/{comment_id}`

Delete own comment only. Admins can delete any.

### `POST /cases/{case_id}/alerts`

Link additional alerts to a case.

```json
{ "alert_ids": ["uuid3", "uuid4"] }
```

Creates a system comment: "Alert {rule_name} linked by {actor}".

### `DELETE /cases/{case_id}/alerts/{alert_id}`

Unlink an alert from a case.

### `GET /cases/facets`

Returns filter counts for sidebar.

```json
{
  "status": [{ "value": "open", "count": 5 }],
  "severity": [{ "value": "high", "count": 3 }],
  "assignee": [{ "value": "alice", "count": 4 }],
  "resolution": [{ "value": "true_positive", "count": 2 }]
}
```

```
[ Search title, description...  ] [Status ▾] [Severity ▾] [Assignee ▾] [Last 7d ▾] [Clear] [Search]
```

**Facet sidebar:** Status, Severity, Assignee, Resolution (collapsed by default).

## Audit Events

| event_type | action | When |
|---|---|---|
| `case.create` | `created` | Case created |
| `case.update` | `updated` | Fields changed |
| `case.close` | `closed` | Status → resolved |
| `case.delete` | `deleted` | Hard delete |
| `case.comment` | `commented` | Comment added |
| `case.link_alert` | `linked` | Alert linked |

All include `resource_type: "case"`, `resource_id: case_id`.

## Technical Notes

- `case_id` and `comment_id` are UUIDs generated server-side (`uuid.uuid4()`).
- All timestamps are naive UTC, consistent with existing DuckDB convention.
- `tags` stored as JSON array string in DuckDB (same pattern as `extra` column in events).
- The `GET /cases/{case_id}` response hydrates `alerts` from the JSONL alerts file by `alert_id` lookup — this may be slow for cases with many alerts if alerts file is large. Acceptable for v1.0; optimize with an alert cache table in v1.1 if needed.
- Comment body max length: 10,000 characters (enforced at API level via Pydantic).
- Analysts can only edit/delete their own comments. Admins can edit/delete any.

## Out of Scope

- Case SLA timers or automated escalation
- Case templates
- Attachments / file uploads
- Case export to PDF
- Linking cases to cases (parent/child)
- Email notification on case assignment (webhook covers this for now)

---

## Open Questions

1. Should a case's severity be independent of linked alerts, or should it auto-derive from the highest linked alert severity? **Decision: independent — analyst sets it manually on creation.**
2. Should resolved cases be visible by default in the case list? **Decision: no — default filter excludes resolved; analyst must select "resolved" filter to see them.**
