# Spec: Log Sources Page (F2)

> Version: v1.0  
> Status: Design  
> Dependencies: v0.9 (events table populated with data)

---

## Problem Statement

Operators currently have no visibility into which log sources are actively sending data to TinySIEM. If a shipper goes silent, the operator won't know until alerts stop firing — a silent failure mode that undermines trust in the SIEM. The Log Sources page solves this by surfacing source health inferred directly from event ingestion activity.

---

## Design Philosophy

**No new collection infrastructure.** Status is derived entirely from the existing `events` table using a single DuckDB query. No heartbeat mechanism, no sidecar agent, no configuration required. A source appears automatically when it first ingests an event and updates its status on every subsequent ingest.

---

## Status Definitions

| Status | Condition | Color |
|---|---|---|
| **Active** | Last event < 30 minutes ago | Green |
| **Stale** | Last event 30 minutes – 24 hours ago | Yellow/amber |
| **Silent** | Last event > 24 hours ago | Red |

Thresholds are configurable via env vars in a later version. For v1.0 they are hardcoded constants in the backend.

---

## Data Model

### No new tables for the list view

The list is derived from a query on the existing `events` table:

```sql
SELECT
    source,
    COUNT(*)            AS event_count,
    MAX(ingested_at)    AS last_seen,
    MIN(ingested_at)    AS first_seen
FROM events
GROUP BY source
ORDER BY last_seen DESC
```

Status is computed server-side from `last_seen` relative to `now()`.

### Optional: `source_registry` table (v1.0 stretch goal)

If operators want to attach metadata (display name, description, owner team, expected sources that haven't sent yet), a registry table can be added. The list view merges registry metadata with query results.

```sql
CREATE TABLE IF NOT EXISTS source_registry (
    source          VARCHAR PRIMARY KEY,
    display_name    VARCHAR,
    description     VARCHAR,
    owner           VARCHAR,
    enabled         BOOLEAN NOT NULL DEFAULT TRUE,
    created_at      TIMESTAMP NOT NULL,
    updated_at      TIMESTAMP NOT NULL
);
```

For v1.0 the registry is optional — the page works without it. If implemented, upsert happens automatically on first ingest of a new source (sets display_name = source, enabled = TRUE).

## API Design

### `GET /sources`

Returns all observed sources with activity stats and computed status. No auth exemption — requires JWT like all endpoints.

**Query params:** none for v1.0.

**Response:**
```json
{
  "sources": [
    {
      "source": "nginx",
      "display_name": "nginx",
      "status": "active",
      "last_seen": "2026-06-29T10:45:00",
      "first_seen": "2026-06-01T00:00:00",
      "event_count_total": 84321,
      "event_count_24h": 1203,
      "event_count_1h": 87
    },
    {
      "source": "syslog_rfc3164",
      "display_name": "syslog_rfc3164",
      "status": "stale",
      "last_seen": "2026-06-29T07:12:00",
      "first_seen": "2026-06-15T08:00:00",
      "event_count_total": 4521,
      "event_count_24h": 12,
      "event_count_1h": 0
    }
  ],
  "summary": {
    "total": 3,
    "active": 1,
    "stale": 1,
    "silent": 1
  }
}
```

`event_count_1h` and `event_count_24h` use `COUNT(*) FILTER (WHERE ingested_at > now() - INTERVAL '...')` in DuckDB.

### `GET /sources/{source}/histogram`

Per-source event volume histogram. Reuses the existing histogram logic from `/events/histogram` but filtered by source.

**Query params:** `start`, `end`, `buckets` (10–200, default 48 for a 24h view).

**Response:** same format as `/events/histogram`.

## Backend Module

No new module needed. Add endpoints to a new `app/sources/router.py` mounted at `/sources`.

```
app/sources/
  __init__.py
  router.py    — GET /sources, GET /sources/{source}/histogram
```

Status computation helper:

```python
_ACTIVE_THRESHOLD_MINUTES = 30
_STALE_THRESHOLD_HOURS = 24

def _compute_status(last_seen: datetime) -> str:
    delta = datetime.utcnow() - last_seen
    if delta.total_seconds() < _ACTIVE_THRESHOLD_MINUTES * 60:
        return "active"
    elif delta.total_seconds() < _STALE_THRESHOLD_HOURS * 3600:
        return "stale"
    else:
        return "silent"
```

## UI Design

### Location

Accessible from the Configuration page as a dedicated section, or as a standalone nav item. Given that it's primarily an ops view (not a daily analyst view), placing it within Configuration → Log Sources tab is preferred over a top-level nav item.

Nav structure remains:
```
Events | Alerts | Cases | Rules | Parsers | Audit Log | Configuration
```

Configuration page tabs: General | Log Sources | Users | (Integrations in v1.2)

### Log Sources tab layout

**Top summary bar:**
```
  ● 1 Active   ● 1 Stale   ● 1 Silent   Last refreshed: 10:45:22  [↻ Refresh]
```

**Sources table:**

## Audit Events

Log Sources is read-only — no write actions, no audit events needed for v1.0.

If the registry (display_name edit) is implemented, `source.update` events should be emitted.

---

## Technical Notes

- The DuckDB query runs at request time, not cached. For < 50 sources and typical event volumes this is fast (< 100ms). If performance becomes an issue, cache the result in memory for 30s.
- `event_count_24h` and `event_count_1h` are computed with conditional aggregation in a single query pass — no separate queries.
- `first_seen` / `last_seen` columns use `MIN` / `MAX` which DuckDB handles efficiently with the `idx_ingested_at` index.
- DuckDB TIMESTAMP has no timezone — comparisons use naive UTC (same convention as the rest of the app).

---

## Out of Scope

- Source heartbeat via dedicated health-check ping (adds new infrastructure; inferred activity is sufficient)
- Alerting when a source goes silent (could be added as a future rule type)
- Per-source retention configuration
- Manual source registration UI (registry upsert on ingest covers discovery automatically)
- Source-specific decoder assignment (already handled by the decoder's `source` field)
