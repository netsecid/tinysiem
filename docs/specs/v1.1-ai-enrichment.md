# Spec: AI Context Enrichment (F4)

> Version: v1.1  
> Status: Design  
> Dependencies: v0.9 (AI parser/rule generation already exists)

---

## Problem Statement

The existing AI generation features (`/parsers/generate`, `/rules/generate`) send minimal prompts to Claude with no context about the deployment environment: what sources are ingesting, what rules already exist, what schema is in use, or what previous generation attempts produced. This forces analysts to manually describe context in the prompt — information TinySIEM already has.

Additionally, analysts have no way to ask Claude to explain a specific alert, map an event to the MITRE ATT&CK framework, or summarize a cluster of events during an investigation.

---

## What Changes

### 1. Schema + context injection for existing generation endpoints

Currently `POST /parsers/generate` and `POST /rules/generate` pass the user's `log_sample` / `description` directly to Claude with a minimal system prompt.

**After enrichment:** each endpoint builds a richer context block prepended to the user's message:

```
<context>
Active log sources: nginx, syslog_rfc3164
Existing parsers: nginx-access (regex, nginx), syslog-rfc3164 (regex, syslog_rfc3164)
Existing rules: http-404-spike (threshold, nginx), brute-force-then-success (correlation, *)
DuckDB schema (events table): [see schema block]
Normalized field names: source_ip, method, uri, status_code, response_size, user_agent, referer
</context>
```

This context is assembled server-side from DuckDB and the loaded decoders/rules lists. No new endpoints.

### 2. Two new AI functions

#### `POST /ai/explain-alert`

Given an `alert_id`, fetch the alert record and the linked event (if available), then ask Claude to explain the alert in plain English.

Request:
```json
{ "alert_id": "uuid" }
```

Response:
```json
{
  "explanation": "This alert fired because the IP address 10.0.0.1 made 15 requests returning HTTP 404 in under 60 seconds. This pattern is consistent with an automated scanner probing for valid URLs. The MITRE technique T1595 (Active Scanning) is a reasonable classification. Recommended action: check whether this IP has prior history in your events table and consider blocking it at the nginx level if it continues.",
  "model": "claude-sonnet-4-6",
  "prompt_tokens": 420,
  "completion_tokens": 180,
  "duration_ms": 1240
}
```

The system prompt instructs Claude to: explain what triggered the rule, describe what this pattern means in a security context, suggest the most likely MITRE ATT&CK mapping, and give a recommended immediate action.

Context sent to Claude:
- The alert record (rule_name, severity, mitre_tactic, mitre_technique, source_ip, summary, triggered_at)
- The originating event record (raw log line, parsed fields) if `event_id` is present in the alert
- The rule definition YAML that fired the alert

#### `POST /ai/analyze-events`

Analyst submits a set of `event_ids` (up to 50) and a `question`. Claude analyzes the events and answers the question.

Request:
```json
{
  "event_ids": ["uuid1", "uuid2", "uuid3"],
  "question": "Are these requests from a single attacker or different sources? What are they trying to access?"
}
```

Response:
```json
{
  "analysis": "All three events originate from the same IP (10.0.0.1) within a 30-second window. They are requesting paths: /admin, /wp-admin, and /phpmyadmin — a pattern consistent with a web scanner looking for common admin interfaces. None of these paths appear to exist based on the 404 responses. This looks like automated reconnaissance rather than a targeted attack. Recommend: add a threshold rule for > 3 requests to admin-pattern URIs per minute.",
  "model": "claude-sonnet-4-6",
  "prompt_tokens": 680,
  "completion_tokens": 220,
  "duration_ms": 1850
}
```

Context sent: all selected event records (raw + parsed fields, truncated to 500 chars per event if needed to stay under context limits).

## New Module

New file: `app/ai/enrichment.py`

```python
async def build_generation_context() -> str:
    """Assembles schema + active sources + existing parsers + rules context block."""

async def explain_alert(alert_id: str, actor: str) -> dict:
    """Fetches alert + event, calls Claude, logs audit event."""

async def analyze_events(event_ids: list[str], question: str, actor: str) -> dict:
    """Fetches events, calls Claude, logs audit event."""
```

Existing `app/ai/claude.py` provides `_get_client()` — `enrichment.py` imports it.

New file: `app/ai/router.py` — mounts at `/ai`:
- `POST /ai/explain-alert`
- `POST /ai/analyze-events`

The existing parser/rule generation endpoints stay in their own routers but import `build_generation_context()` from `enrichment.py`.

## API Design

### `POST /ai/explain-alert`

Auth: analyst role or above.

Request:
```json
{ "alert_id": "uuid" }
```

Response: `200` with explanation object (see above). Returns `404` if alert not found. Returns `503` if `TINYSIEM_CLAUDE_API_KEY` is not set.

### `POST /ai/analyze-events`

Auth: analyst role or above.

Request:
```json
{
  "event_ids": ["uuid1", "uuid2"],
  "question": "What is this attacker doing?"
}
```

Constraints:
- `event_ids`: 1–50 items (Pydantic validation, 422 if exceeded)
- `question`: max 2000 chars

Response: `200` with analysis object. `503` if no API key.

## Changes to Existing Generation Endpoints

### `POST /parsers/generate`

Before calling Claude, call `build_generation_context()` and prepend the context block to the user message. No change to request/response schema.

### `POST /rules/generate`

Same treatment. No change to request/response schema.

## UI Changes

### Alerts page

Each expanded alert row gains an **"Explain with AI"** button. On click:

1. Sends `POST /ai/explain-alert` with the alert's `alert_id`
2. Shows a loading spinner in the expanded row
3. Renders the explanation text in a bordered box below the alert fields

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✦ AI Analysis
This alert fired because the IP address 10.0.0.1 made
15 requests returning HTTP 404 in under 60 seconds...

Recommended action: check whether this IP has prior
history and consider blocking at the nginx level.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

The explanation is rendered fresh on each click (not cached in localStorage). If `TINYSIEM_CLAUDE_API_KEY` is not set, the button is grayed out with tooltip "AI features require TINYSIEM_CLAUDE_API_KEY".

### Events page

Multi-select on event rows (checkbox column appears when any row is hovered). When 2+ rows are selected, an **"Analyze with AI"** button appears in the top-right:

1. Click opens a small modal with a text area for the question (pre-filled: "What do these events have in common?")
2. Sends `POST /ai/analyze-events` with selected event IDs and question
3. Shows streaming response in the modal (or full response if streaming not implemented)

The checkbox column is hidden by default and appears only on hover — matches the Datadog pattern of progressive disclosure.

### Case detail panel

In the case comments thread, an **"Ask AI"** input field appears at the top of the comment area. Submitting it calls `POST /ai/analyze-events` with all alerts linked to the case, using the typed question. The response is inserted as a new comment with `is_system = TRUE` and author `"ai-assistant"`.

## Audit Events

| event_type | action | detail |
|---|---|---|
| `ai.call` | `explain_alert` | alert_id, model, prompt_tokens, completion_tokens, duration_ms, prompt_preview (5000 char truncation) |
| `ai.call` | `analyze_events` | event_ids (list), question (truncated), model, token counts, duration_ms |

These follow the same audit pattern already established for parser/rule generation.

---

## Token Budget

To avoid unexpectedly large Claude API calls:

- `explain_alert`: raw event log truncated to 2000 chars; rule YAML included in full
- `analyze_events`: each event's `raw` field truncated to 500 chars; max 50 events; total context estimated ~25k tokens max
- `build_generation_context()`: decoders and rules truncated to name + source only (not full YAML) unless count < 10

If the assembled context exceeds 50k tokens (estimated), the function drops the oldest/least-relevant items and logs a warning. This is a safeguard, not expected behavior.

## Environment Variables

No new variables beyond the existing `TINYSIEM_CLAUDE_API_KEY`.

---

## Out of Scope

- Streaming response (AI text appears word-by-word). Full response returned at once.
- Agent/tool-use mode (Claude calling back into TinySIEM APIs). Plain text generation only.
- Fine-tuning or prompt storage/versioning
- Cost tracking per user (total token usage is logged in audit but not per-user billing)
- AI-powered triage automation (no auto-closing of alerts based on AI response)
