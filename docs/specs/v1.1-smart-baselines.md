# Spec: Smart Baselines (F3)

> Version: v1.1  
> Status: Design  
> Dependencies: v1.0, several weeks of ingested event history for meaningful baselines

---

## Problem Statement

Static threshold rules (e.g., "fire if > 10 requests per minute") require manual tuning and produce constant false positives or miss anomalies during off-peak hours. A traffic spike at 3am is very different from the same spike at 2pm. Baselines solve this by learning what "normal" looks like per-source, per-hour-of-day, and per-day-of-week — then alerting when observed traffic deviates significantly from the learned pattern.

---

## Approach: Statistical Z-Score

No ML models. No sklearn. `numpy` only.

For each source, TinySIEM maintains a bucket for every `(hour_of_day, day_of_week)` combination — 168 buckets per source. Each bucket accumulates the event count seen in that bucket across historical windows. When a new window closes, the observed count is compared to the bucket's mean and standard deviation using a z-score:

```
z = (observed - mean) / std_dev
```

A z-score above the configured threshold (default: 3.0) triggers a baseline violation.

**Why z-score:**
- Simple and interpretable ("this is 3 standard deviations above normal")
- Adapts automatically as history accumulates — no manual tuning
- Handles seasonal patterns (weekend vs weekday, night vs day) via bucket granularity
- Explainable to analysts: "Normal traffic on Monday at 2pm is 120 ± 30 req/min. We saw 410."

**Minimum data requirement:** a bucket needs at least 4 samples before it will generate violations (to avoid triggering on the first data points). Buckets with `n < 4` are silently skipped.

## Data Model

### New Table: `baselines`

Stores per-bucket statistics. Updated incrementally by the background job.

```sql
CREATE TABLE IF NOT EXISTS baselines (
    baseline_id     VARCHAR PRIMARY KEY,  -- uuid
    source          VARCHAR NOT NULL,
    hour_of_day     INTEGER NOT NULL,     -- 0-23
    day_of_week     INTEGER NOT NULL,     -- 0=Monday ... 6=Sunday
    mean            DOUBLE NOT NULL,
    std_dev         DOUBLE NOT NULL,
    sample_count    INTEGER NOT NULL,     -- number of windows accumulated
    last_updated    TIMESTAMP NOT NULL,
    UNIQUE (source, hour_of_day, day_of_week)
);
```

### New Table: `baseline_violations`

Records each detected anomaly. Kept for 90 days (same retention as events).

```sql
CREATE TABLE IF NOT EXISTS baseline_violations (
    violation_id    VARCHAR PRIMARY KEY,
    source          VARCHAR NOT NULL,
    detected_at     TIMESTAMP NOT NULL,
    hour_of_day     INTEGER NOT NULL,
    day_of_week     INTEGER NOT NULL,
    observed_count  DOUBLE NOT NULL,
    expected_mean   DOUBLE NOT NULL,
    expected_std    DOUBLE NOT NULL,
    z_score         DOUBLE NOT NULL,
    severity        VARCHAR NOT NULL,     -- low | medium | high | critical
    acknowledged    BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE INDEX IF NOT EXISTS idx_bv_detected ON baseline_violations(detected_at);
CREATE INDEX IF NOT EXISTS idx_bv_source   ON baseline_violations(source);
```

**Severity mapping from z-score:**

| Z-score | Severity |
|---|---|
| 3.0 – 4.0 | low |
| 4.0 – 5.0 | medium |
| 5.0 – 7.0 | high |
| > 7.0 | critical |

## Background Job

A lightweight background task runs every 5 minutes (configurable via `TINYSIEM_BASELINE_INTERVAL_MINUTES`).

**Algorithm per run:**

```
1. For each unique source in events table:
   a. Compute current window: count events in [now - 5min, now]
   b. Determine bucket: (current.hour_of_day, current.day_of_week)
   c. Fetch existing baseline for (source, hour, dow) from baselines table
   d. If baseline exists and sample_count >= 4:
      - Compute z = (observed - mean) / max(std_dev, 1.0)  # floor std_dev at 1.0 to avoid div-by-zero
      - If z > TINYSIEM_BASELINE_Z_THRESHOLD (default 3.0):
          * Insert into baseline_violations
          * Write alert to JSONL alerts file (reuse existing alert writer)
   e. Update baseline (online mean/std update using Welford's algorithm):
      - sample_count += 1
      - delta = observed - mean
      - mean += delta / sample_count
      - delta2 = observed - mean
      - M2 += delta * delta2  (sum of squared deviations)
      - std_dev = sqrt(M2 / sample_count) if sample_count > 1 else 0.0
   f. Upsert baseline record
```

**Welford's online algorithm** is used so baselines update incrementally without storing all historical values. The `baselines` table stores only `(mean, std_dev, sample_count, M2)` — not raw window values.

**Note:** `M2` (sum of squared deviations) needs to be stored to support online std_dev updates. Add `m2` column to `baselines` table:

```sql
ALTER TABLE baselines ADD COLUMN m2 DOUBLE NOT NULL DEFAULT 0.0;
```

### Background job startup

The job starts in `main.py` lifespan using `asyncio.create_task`:

```python
async def _baseline_loop():
    while True:
        try:
            await baseline_engine.run_once()
        except Exception as e:
            logger.error(f"Baseline job error: {e}")
        await asyncio.sleep(settings.baseline_interval_minutes * 60)
```

## API Design

### `GET /baselines`

List all baseline buckets with current statistics.

**Query params:** `source` (filter), `hour_of_day`, `day_of_week`.

**Response:**
```json
{
  "baselines": [{
    "source": "nginx",
    "hour_of_day": 14,
    "day_of_week": 0,
    "mean": 120.5,
    "std_dev": 28.3,
    "sample_count": 42,
    "last_updated": "2026-06-29T14:05:00"
  }]
}
```

### `GET /baselines/violations`

List detected anomalies.

**Query params:** `source`, `severity`, `acknowledged` (bool), `start`, `end`, `limit`, `offset`.

**Response:**
```json
{
  "total": 5,
  "violations": [{
    "violation_id": "uuid",
    "source": "nginx",
    "detected_at": "2026-06-29T03:15:00",
    "hour_of_day": 3,
    "day_of_week": 0,
    "observed_count": 410,
    "expected_mean": 12.0,
    "expected_std": 4.5,
    "z_score": 88.4,
    "severity": "critical",
    "acknowledged": false,
    "summary": "nginx traffic at Mon 03:00 was 410 events (expected 12 ± 4.5, z=88.4)"
  }]
}
```

### `PATCH /baselines/violations/{violation_id}`

Acknowledge a violation (analyst confirms they've reviewed it).

```json
{ "acknowledged": true }
```

### `DELETE /baselines/{source}`

Reset all baseline buckets for a source. Useful when a source's traffic pattern changes structurally (e.g., after a major traffic increase from new customers). Requires `admin` role. Audit logged.

## Technical Notes

- The baseline job runs in the same process as the FastAPI app — no separate worker process needed at this scale.
- DuckDB's single writer model means the baseline job must acquire `_lock` before writing (same lock used by all DuckDB operations). The job is async but wraps DuckDB writes in `loop.run_in_executor` to avoid blocking the event loop.
- `std_dev` floored at `1.0` in z-score computation prevents division-by-zero when a source's traffic is perfectly constant.
- Baseline violations also fire the regular alert writer, so they appear in `GET /alerts` alongside rule-based alerts. The `rule_name` field is `"smart_baseline"` to distinguish them.
- Violation `summary` field is human-readable: `"{source} traffic at {dow} {hour}:00 was {observed} events (expected {mean:.0f} ± {std:.0f}, z={z:.1f})"`.

## Open Questions

1. Should baselines run on all sources automatically, or should operators opt-in per source? **Decision: opt-in global toggle (TINYSIEM_BASELINES_ENABLED), default true. No per-source configuration in v1.1.**
2. How long until baselines are meaningful? **With 5-minute windows and 168 buckets, a source needs ~840 windows (70 hours) to fill all buckets to the minimum 4-sample threshold. Display "learning..." badge on buckets with < 4 samples.**
