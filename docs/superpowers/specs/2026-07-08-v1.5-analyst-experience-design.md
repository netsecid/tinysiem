# v1.5 — "Analyst Experience": The Features a SOC Analyst Reaches For Every Shift

> Status: Approved design
> Date: 2026-07-08
> Depends on: v1.4 "Hardened Tiny" (ships first)

## Context

v1.4 hardens the platform; v1.5 closes the gaps a senior SOC analyst hits the moment an
investigation starts. Designed from the daily analyst loop: triage → pivot on an indicator →
check against known-bad → hunt around the timeframe → tune the noisy rule → report out.
TinySIEM's triage loop (dashboard → alert queue → tabbed modal → case → playbook) is solid;
everything investigative after the first click is missing.

Constraints carried over from the project charter: **zero new Python dependencies**, no
build-step frontend, DuckDB + single-file HTML pages only.

## E1. Entity pivot view

*"Who is this IP? Have I seen it before?" — the first question of every investigation.*

- New endpoint `GET /entities/ip/{value}` (analyst+) returning, from existing tables:
  - `first_seen` / `last_seen` / total event count
  - event histogram over the last 7 days (reuses histogram bucketing)
  - top sources, methods, URIs, status codes for the IP (facet-style)
  - related alerts (alerts JSONL filtered by `source_ip`)
  - related cases (via alerts → `case_alerts` join)
- New `ui/entity.html?ip=<value>` page following the single-file convention.
- Every IP rendered in Events, Alerts, and Cases pages becomes a link to the entity view.
- v1.5 scope is IP entities only (the one first-class indicator in the schema). Usernames
  and other actors live inside `extra` JSON for cloud sources — deferred until a normalized
  actor field exists.
- No new storage: this is a read-only composition of existing queries.

## E2. IOC watchlists

*The #1 detection type in every SOC: match against a list of known-bad. The rule engine
matches patterns; it cannot express "any of these 5,000 indicators."*

- New DuckDB table `watchlist_entries`:
  `(id VARCHAR PK, list_name VARCHAR, indicator_type VARCHAR, value VARCHAR,
   severity VARCHAR, note VARCHAR, added_by VARCHAR, added_at TIMESTAMP, active BOOLEAN)`.
  Rows are updated (`active` toggle) → **no secondary index** (DuckDB 1.1.3 constraint).
- Indicator types: `ip` (exact), `cidr`, `user_agent_substring`, `uri_substring`.
- CRUD API under `/watchlists` (write admin+, read analyst+), plus CSV import
  (`POST /watchlists/import`, columns: type,value,severity,note) and paste-friendly bulk add.
  All writes audit-logged. Entry cap (50,000) keeps memory bounded.
- Ingest pipeline check: module-level in-memory cache (same pattern as `_decoders`/`_rules`),
  rebuilt on any watchlist write — exact IPs in a set, CIDRs as `ipaddress` networks,
  substrings as a scan list. On hit, an alert is emitted with
  `rule_name = "watchlist:<list_name>"`, the entry's severity, and the note in the summary.
- Doubles as **watch mode**: put an entity under investigation on a list and get alerted
  when it reappears.

## E3. Rule backtesting

*"What would this rule have fired on last week?" Deploying blind and counting the damage
the next morning is not a tuning workflow.*

- `POST /rules/{name}/backtest` (admin+) with body `{"days": 7}` (1–30).
- `field_match` conditions translate directly to a parameterized WHERE against `events`.
  `threshold` conditions evaluate against fixed consecutive windows of `window_seconds`
  (documented as an approximation of the live sliding window — good enough for tuning).
  `correlation` rules return `{"supported": false}`.
- Response: `would_fire_count`, per-day counts, and up to 20 sample matching events.
- Also accepts an inline rule body (`POST /rules/backtest`) so a rule can be tested
  **before** saving — pairs with the AI rule generator: generate → backtest → deploy.
- UI: "Backtest" button in the rule detail panel rendering counts + samples.
- Read-only against existing data; query capped by the existing `_lock` discipline.

## E4. Saved searches + shareable deep links

*Analysts re-run identical hunts every shift and paste findings to teammates.*

- New DuckDB table `saved_searches`
  `(id VARCHAR PK, owner VARCHAR, name VARCHAR, page VARCHAR, query_string VARCHAR,
   created_at TIMESTAMP)`. Insert/delete only — no UPDATE, no index concerns.
- API: `GET/POST/DELETE /searches` (analyst+, owner-scoped).
- Deep links: the Events and Alerts pages serialize their current filter state into the URL
  (`history.replaceState`) and hydrate from URL params on load. Any view becomes a pasteable
  link for case comments and shift handover.
- UI: a saved-searches dropdown on Events and Alerts — save current, run, delete.

## E5. Per-rule exceptions

*v1.4's suppression window fixes repetition; it does not fix known false positives.
Tuning by disabling a whole rule is the industry's worst practice.*

- New DuckDB table `rule_exceptions`
  `(id VARCHAR PK, rule_name VARCHAR, field VARCHAR, value VARCHAR, reason VARCHAR,
   added_by VARCHAR, added_at TIMESTAMP)`. Insert/delete only.
- `field` limited to the same allowlist as `count_events_in_window` (`_ALLOWED_FIELDS`).
- Rule engine consults an in-memory exception cache at evaluation entry: if the event
  matches an exception for that rule, the event is skipped for that rule entirely
  (including threshold counting). The event itself is still ingested and searchable.
- API under `/rules/{name}/exceptions` (admin+; `reason` mandatory; audit-logged both ways).
- UI: exceptions list in the rule detail panel; a "add exception" shortcut in the alert
  modal pre-filled with the alert's rule + source_ip.

## E6. CSV export

- `format=csv` query param on `GET /events` and `GET /alerts`, honoring all active filters.
- Streams via stdlib `csv` with proper quoting; `Content-Disposition: attachment`.
  Row cap 10,000 per export (documented) to bound memory.
- UI: "Export CSV" button beside the existing filters on both pages.

## E7. MITRE ATT&CK coverage matrix

*Rules already carry `mitre_tactic`/`mitre_technique`; nothing renders them.*

- `GET /rules/mitre-coverage` (analyst+): techniques grouped by tactic with rule counts and
  rule names, computed from loaded rules.
- UI: a coverage section on the Rules page — the 14 Enterprise tactic columns (static
  list, hardcoded), technique cells colored by rule count, empty tactics visibly empty
  (gaps are the point). Only techniques referenced by rules are listed; the full ATT&CK
  dataset is **not** bundled (tiny).

## Considered and deliberately left out

- **GeoIP enrichment** — needs a MaxMind database + reader dependency; watchlists cover
  "known bad" without it. Revisit on demand.
- **Threat-intel feed ingestion (TAXII/MISP/OTX)** — heavy clients, polling infrastructure,
  format zoo. The CSV import in E2 is the tiny interop story (export from any TIP → import).
- **UEBA-style entity risk scoring** — baselines already provide z-score anomalies.
- **Notebook-style hunting UI** — Events + saved searches + deep links is the tiny answer.
- **Username/actor entities** — blocked on a normalized actor field in the events schema;
  candidate for v1.6 alongside it.

## Testing

- E1: entity endpoint composition (counts, alerts/cases joins) with seeded fixtures.
- E2: CRUD + import validation, cache rebuild on write, ingest-path hit → alert for each
  indicator type, cap enforcement, inactive entries ignored.
- E3: field_match backtest counts vs seeded events; threshold windowing; inline-rule
  variant; correlation → unsupported.
- E4: owner scoping (user A cannot see/delete user B's searches).
- E5: excepted event skipped for the rule but present in /events; threshold counting
  excludes excepted events; reason required.
- E6: quoting/injection-safe CSV (fields containing commas, quotes, newlines), row cap.
- E7: coverage aggregation from loaded rules.
- All tests run inside Docker (`docker-compose exec -w /app tinysiem pytest app/tests/`).

## Release housekeeping

- New tables: `watchlist_entries`, `saved_searches`, `rule_exceptions` (the DuckDB
  no-secondary-index constraint note in CLAUDE.md gains `watchlist_entries`).
- No new Python dependencies, no new env vars.
- Deferred-to-v1.6+ list (carried from v1.4 plus this release): TOTP/2FA, dependency
  extras split, audit-log hash chaining, GeoIP, actor/username entities.
