# v1.4 — "Hardened Tiny": Security Controls, SOC Quality of Life, Footprint Reduction

> Status: Approved design
> Date: 2026-07-08
> Depends on: v1.3 (playbooks + alert enrichment) — shipped

## Context

A full implementation review after v1.3 found a solid security baseline (parameterized SQL
with a field allowlist, JWT + 3-role RBAC, timing-safe API key comparison, dummy-hash
anti-enumeration on login, Fernet-encrypted integration credentials, audit logging,
`yaml.safe_load`, non-root container, security headers middleware) but a set of gaps that
matter for a tool whose entire job is security. Guiding principles for this release, in order:

1. **Security controls are mandatory features, not nice-to-haves.** Every Track A item ships.
2. **Tiny footprint.** No new Python dependencies anywhere in this release; one large
   dependency is removed. No new services, no build-step frontend.
3. **Day-to-day SOC usability.** Alert fatigue and data loss are operational security
   problems, so noise control and backup are in scope.

## Track A — Mandatory Security Controls

### A1. Login brute-force lockout

- In-memory failed-attempt tracker in `app/auth_router.py`, keyed on `(username, source_ip)`.
- 5 consecutive failures → lockout with exponential backoff (base 60s, doubling, capped at
  15 minutes). Successful login resets the counter.
- Locked-out attempts return 429 with a generic message (no confirmation the account exists)
  and are audit-logged as `auth.lockout`.
- In-memory is deliberate: state loss on restart is acceptable; no new table, no dependency.
- Scope note: CLAUDE.md's "no rate limiting" rule stands for API-wide rate limiting. Lockout
  on `/auth/login` is an authentication control and is explicitly carved out.

### A2. Forced password change + password policy

- New `must_change_password BOOLEAN` column on `users`. Set on the seeded superadmin when it
  is created with the default password, and settable by superadmins when creating/resetting
  users.
- While the flag is set, every authenticated endpoint except `/auth/me`, `/auth/logout` and a
  new `POST /auth/change-password` returns 403 with `{"code": "password_change_required"}`.
  The UI login flow detects this and shows a change-password form.
- `POST /auth/change-password` takes `current_password` + `new_password`, verifies the
  current one, clears the flag, and bumps `token_epoch` (see A3).
- Password policy: minimum 12 characters, enforced in `/auth/change-password` and all
  `users/` create/update paths. Length only — no composition rules (NIST-aligned, tiny).

### A3. Token revocation via token epoch

- New `token_epoch INTEGER DEFAULT 0` column on `users`. JWT payload gains an `epoch` claim.
- `require_auth` compares the token's epoch against the user's current epoch (single
  primary-key lookup by user id; respects the existing `_lock`); mismatch → 401.
- Epoch is bumped on: password change, role change, user update by a superadmin, user delete
  (row gone → 401 naturally), and the new `POST /auth/logout` (revokes all of the caller's
  tokens — "log out everywhere" semantics, acceptable for tiny).
- DuckDB constraint reminder: `users` must not gain a secondary index (UPDATE breaks with
  PK + secondary index on DuckDB 1.1.3).

### A4. Scope the global API key to ingest only

- `TINYSIEM_API_KEY` stops mapping to an admin `AuthUser`. It authenticates only paths under
  `/ingest/` (raw, file, beats), as role `ingest`.
- Everything else requires a JWT. **Breaking change** — documented in the changelog and
  `docs/configuration.md`. Log shippers are unaffected; humans/scripts using the API key for
  queries must switch to a user login.
- Implementation: `require_auth` accepts the API key only when the route dependency asks for
  the new `ingest` capability; `_ROLE_HIERARCHY` is untouched (ingest is not in the hierarchy).

### A5. Syslog listener guardrails

- New env vars: `TINYSIEM_SYSLOG_ALLOW_CIDRS` (comma-separated CIDRs; empty = allow all,
  preserving current behavior) and `TINYSIEM_SYSLOG_MAX_BYTES` (default 8192).
- UDP datagrams / TCP lines from non-allowlisted sources or over the size cap are dropped
  and counted; `/health` gains `listeners.syslog_dropped` counters.
- Uses stdlib `ipaddress` — no new dependency. TLS syslog stays out of scope.

### A6. CSP header + self-hosted fonts

- IBM Plex Sans + IBM Plex Mono (woff2, the used weights only) vendored into `ui/fonts/`
  with an `ui/fonts.css`; all 10+ UI pages switch from Google Fonts links to it. TinySIEM
  then makes zero external requests at runtime — air-gap friendly.
- `security_headers` middleware adds `Content-Security-Policy` on `/ui` responses:
  `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
  img-src 'self' data:; font-src 'self'; connect-src 'self'; frame-ancestors 'none';
  base-uri 'none'; form-action 'self'`.
- `'unsafe-inline'` is required by the single-file HTML convention and is accepted;
  the win is locking `connect-src`/`font-src`/`img-src`/`frame-ancestors`, which blocks
  exfiltration targets and remote script loads even if an XSS slips through.

### A7. CORS tightened

- Default changes from `allow_origins=["*"]` to same-origin only (no CORS middleware unless
  configured). New `TINYSIEM_CORS_ORIGINS` (comma-separated) restores cross-origin access
  for anyone pointing a UI at a remote API endpoint.
- The login page's configurable "endpoint" field keeps working when the operator sets the
  env var; docs updated.

### A8. Built-in TLS

- New env vars `TINYSIEM_TLS_CERT` / `TINYSIEM_TLS_KEY`; when both are set, the container
  entrypoint passes `--ssl-certfile/--ssl-keyfile` to uvicorn. No new dependency.
- `docs/configuration.md` gains a section with a one-line `openssl` self-signed cert recipe
  and a note on mounting certs into the container.

### A9. Startup guardrails

- Refuse to start (clear fatal log) when `TINYSIEM_JWT_SECRET` is shorter than 32 characters.
- Loud startup warning when the superadmin still has the default password (checkable via the
  `must_change_password` flag from A2).
- Startup warning when integrations rows exist but `TINYSIEM_MASTER_KEY` is unset.

### A10. `/sbom` endpoint

- `GET /sbom` (admin+) returning the installed dependency inventory (name, version) generated
  at build time from `pip freeze` into a static JSON file baked into the image. Already
  blessed as in-scope by the roadmap's out-of-scope note ("a static /sbom endpoint is
  sufficient").

## Track B — SOC Quality of Life

### B1. Alert suppression

- Optional `suppress_seconds` field in rule YAML (default 300 for threshold rules, 0 = off).
- After a rule fires for an entity (rule name + `source_ip`), further firings for the same
  pair are suppressed until the window elapses. Suppressed count is accumulated and stamped
  onto the next emitted alert as `suppressed_count`.
- State is in-memory in the rule engine (restart clears it — acceptable).

### B2. Self-monitoring

- Security-relevant audit events (`auth.login` failures, `auth.lockout`, `user.*`,
  credential/integration changes) are additionally fed through the ingest pipeline as
  source `tinysiem_internal` (JSON decoder).
- One new built-in rule ships: brute-force detection (threshold on failed logins per IP),
  so the SIEM alerts on attacks against itself even before lockout triggers.
- Loop guard: events from `tinysiem_internal` never generate further internal events.

### B3. Backup / restore

- `POST /admin/backup` (superadmin) streams a tar.gz containing: a consistent DuckDB export
  (`EXPORT DATABASE` to a temp dir under the existing `_lock`), the alerts JSONL, and custom
  rules/parsers YAML.
- Restore is documented as a manual procedure (stop container, unpack into the volume,
  start) in a new `docs/backup.md`. No restore endpoint — restoring a live database is
  where tiny stops.

## Track C — Footprint Reduction

### C1. Remove chromadb

- Delete `app/storage/chroma_store.py`, the ingest-pipeline upsert call, the
  `TINYSIEM_CHROMA_PATH` setting, the `chromadb` requirement, and the conftest stub.
- No shipped feature reads from ChromaDB; AI enrichment talks to the Claude API directly.
- Largest single image-size reduction available (chromadb pulls onnxruntime and friends).
- Existing `chroma_store` data directories in deployed volumes are simply orphaned; a
  changelog note tells operators they may delete `/app/data/chroma_store`.

## Considered and deferred

- **TOTP/2FA** — real value, but adds a dependency and enrollment UX; v1.5 candidate.
- **Optional extras split for boto3 / google-api-python-client** — complicates the
  single-image Docker build for ~80 MB; revisit if image size is still a complaint after C1.
- **Audit-log hash chaining / tamper evidence** — overkill at this scale; the audit table
  plus B3 backups is the answer for now.
- **API-wide rate limiting** — still out of scope (A1 lockout is the only carve-out).

## Testing

- Every Track A item gets endpoint-level tests (lockout timing via injected clock, 403
  password-change gate, epoch revocation, API-key-on-non-ingest 401, CIDR drop, CSP header
  presence, weak-JWT-secret refusal via settings override).
- B1/B2 get rule-engine tests (suppression window, internal-source loop guard).
- B3 gets an archive-contents test.
- C1: full test suite passes with the stub removed from conftest.
- All tests run inside Docker (`docker-compose exec -w /app tinysiem pytest app/tests/`).
